# Tattoo Portal email verification — Phase 5

**For review only. Production Firebase, real accounts, email delivery settings, Firestore rules, payments and Resend activation were not accessed or changed.** This branch starts from shared development commit `602f25d` (merged PR #38). Retain `fawcett-website-sandbox` as production; leave `fawcett-website` untouched. Codex uses only `demo-fawcett-dev` Auth/Firestore emulators and fictional `@example.test` accounts.

## User behaviour

All four signup entry points (`TattooPortalLogin`, `ConsultRequestForm`, `MembershipApplicationForm`, `ClientMessages`) request a verification link through the same nonthrowing helper after Firebase registration. A failed request leaves the created account intact and does not reject an otherwise valid intake/profile workflow. Standalone portal signup opens `/portal/verify-email`; the existing founders destination remains intact. Form-based signup stays on its current intake/message flow. Requests have bounded network timeouts; there is no automatic retry loop.

New and existing unverified users see a black, white and blue reminder with a link to **Verify your email**. The screen offers resend, a visible countdown and **I’ve verified my email — check again**, along with **Continue to my portal**. Access to history, consultation submission and private messaging is not conditioned on verification. The banner never sends email on login, page load or focus. There is no bulk verification campaign for existing users.

Arrival at the verification screen reloads persisted Auth state and refreshes the ID token once per signed-in UID. Returning to a visible/focused browser tab also refreshes status, throttled to once per five seconds. Manual refresh supports hosted Firebase callbacks, another tab/device or an expired session. The application does not write a separate Firestore verification flag or grant any admin role.

Firebase’s default hosted email-action handler can consume the link and offer **Continue** to the fixed portal verification screen. No custom handler change is necessary for that flow. If the owner later configures this application as a custom verification handler, it supports only `mode=verifyEmail`: it checks the code using the configured SDK/project, asks the user to confirm, applies the code, reloads the user and refreshes their token. A wrong signed-in account must sign out before applying it. Signed-out verification is allowed using the email’s action code, followed by normal sign-in.

Invalid, expired and already-used links offer safe recovery text and a fresh-link route. Firebase may classify a replay as `invalid-action-code`; the screen does not falsely distinguish all such cases or infer account ownership from an error. Expired/replayed codes never set application flags. No link-provided `continueUrl` or `returnTo` is followed. Other modes (password reset, recovery, email change), foreign API keys, tenants, duplicate action parameters and malformed codes are rejected. The action query is removed from browser history on arrival, the route is dynamic/no-store, and response/meta referrer policy is `no-referrer`. There is no analytics or action-code logging in this feature. Hosting/access-log retention must still be reviewed: the initial HTTP URL necessarily arrives at the hosting service.

## Sending and abuse protection

`POST /api/auth/verification` requires a current Firebase bearer token with revocation checking; the server rereads the enabled Auth user. The empty request accepts no recipient, sender, UID, action type or redirect input. Firebase sends a `VERIFY_EMAIL` action to the account’s current Auth address through `accounts:sendOobCode` using that user’s token. Already verified users receive an idempotent status response without another email. No Admin-generated links, passwords or new Auth accounts are created by this API.

A private Firestore transaction reserves **both UID and normalized-mailbox budgets**, with a 60-second cooldown and at most five send attempts per rolling 24-hour window. Concurrency, page reloads, address changes and deletion/recreation of the same mailbox cannot bypass those budgets. HTTP 429 includes `Retry-After`; the screen reads the durable server cooldown. Provider outages, rejected sends and uncertain outcomes consume their reserved slot too. There is no automatic verification-mail retry, no external-email idempotency claim and no action-code/recipient/token stored in limiter documents. `authVerificationRateLimits` contains only hashed identity keys and bounded lists of recent attempt timestamps and is denied to every browser role by existing default-deny rules. GET returns only the signed-in user’s verification/cooldown status with no-store headers.

**Limit of this protection:** Firebase’s client Auth API key is public. A modified client can call Firebase’s own verification endpoint outside this application route. This feature cannot impose its server limits on those direct Firebase calls or prevent creation of many different mailboxes. Firebase project quotas/abuse controls, signup protections, monitoring and any supported project-level App Check/Identity Platform/reCAPTCHA controls must be reviewed by the owner before live activation. Do not claim the countdown alone prevents abuse or invent a trusted IP from arbitrary forwarded headers. No project-level security setting is altered by this PR.

## Isolation and configuration

Local mode always uses the fixed Auth emulator URL at `127.0.0.1:9099`, never a remote Firebase URL. Only fictional `@example.test` addresses can be sent local verification actions, and the Auth emulator records action links instead of delivering email. Next Preview remains emulator-only; a hosted Preview without local emulators cannot perform Auth workflows and must not be connected to production to make them work.

| Setting | Local behaviour / later production prerequisite |
| --- | --- |
| `EMAIL_VERIFICATION_ENABLED` | Defaults off for live delivery; must be exact `true` in a separately approved Production rollout. Emulator delivery remains synthetic and available even with this live switch false. |
| `EMAIL_VERIFICATION_ORIGIN` | Defaults to `http://localhost:3000` in emulators. Optional loopback-only origin for another local port. Live mode requires an explicit canonical HTTPS origin with no credentials, path, query or fragment. The server appends `/portal/verify-email`. |
| Existing Firebase configuration | Keep all existing emulator guards. Live mode requires genuine Vercel Production context and both public/Admin project IDs equal to `fawcett-website-sandbox`. No credentials are needed or permitted in Codex. |

Live verification defaults disabled independently of `NOTIFICATIONS_MODE` and `NOTIFICATIONS_ENABLED`. Resend and payments remain disabled. Firebase verification email is a separate external delivery capability; enabling it requires its own owner approval. Do not supply a Resend key or Firebase service-account key for local verification. No reusable cloud setup changes or new dependencies are necessary.

## Email changes and existing notification policy

There is no existing self-service email-change UI or application call to `updateEmail`/`verifyBeforeUpdateEmail`. This PR does not add one, copy contact details into Auth or automatically link accounts. A changed email must be verified in its own right. Completion reloads the current account before comparing the link target, so a cached old browser address is not accepted as proof for a newly changed address. Tests verify that normal SDK `updateEmail` resets `emailVerified` and token claims and that a stale old-address code is rejected.

Any future self-service change should use Firebase `verifyBeforeUpdateEmail` with recent reauthentication and proof of the new mailbox, strict return URLs, appropriate recovery notices and separately tested change/recovery handlers. Do not have an admin mark a new real address verified to bypass proof. Firebase Admin can explicitly set verification flags; that power is outside the application workflow and must remain restricted. Existing CRM email fields are not silently rewritten during verification; any studio contact-detail update/account-linking remains a reviewed CRM operation.

The Phase 4B worker still uses **current server-side Auth email and `emailVerified`**, not browser claims, form contact email or a matching studio record. Verification does not enable Resend, release held jobs or replay historical confirmations/messages. Future eligible records may notify only after notification activation is separately approved. Earlier held notices remain visible to operators for reviewed reconciliation, and all conversation contents remain in the portal. A first consultation submitted before mailbox verification can therefore remain without a client email confirmation; the studio/portal record still succeeds. Do not reset notification deduplication keys to replay it automatically.

## Local setup and manual rehearsal

1. Use the existing `/workspace/fawcett-website` checkout and installed npm/Java setup. Start `npm run emulators` and, in a separate terminal, `npm run dev`. Use only fictional `@example.test` accounts. Keep Resend/payments off.
2. Register through any of the four signup entry points. Open `/portal/verify-email`; confirm portal navigation and private history still work while pending. The emulator terminal prints the verification URL, and its local OOB-code endpoint exposes fictional codes for testing. These are test-only links, never real records.
3. Use the emulator’s normal link to verify, then follow Continue to the portal and confirm status refresh. To exercise the custom application handler, use the emulator code in `http://localhost:3000/portal/verify-email?mode=verifyEmail&oobCode=THE_SYNTHETIC_CODE&apiKey=demo-fawcett-api-key`. The emulator’s own link uses `fake-api-key`; do not copy that fake key into a custom application link or change the SDK’s project configuration. No code or email value belongs in committed files or screenshots/logs shared outside the synthetic test.
4. Test resend on another fictional account: rapid concurrent requests should permit one send, then show the cooldown. A browser reload must not reset it. Reopen a used code and try a malformed link; both must offer recovery without modifying account identity. Try a wrong signed-in account; it must not consume the link.
5. `npm run test:verification` starts/stops its own Auth/Firestore emulators, creates fictional accounts and clears only the fixed demo database. Stop only your own manual emulator processes first to free ports. `npm test`, `npm run lint` and `VERCEL_ENV=preview npm run build` are the complete validation workflow.

The tests use the real Firebase Auth/Firestore SDKs, bearer verifier, HTTP send API and emulator action codes. They cover valid/invalid/replayed verification, cross-account and signed-out handling, token refresh, concurrency/durable limits, mailbox recreation, provider failures, private limiter access, unchanged history, pending notification withholding, address changes, source project validation and nonthrowing signup delivery failures. The Auth emulator does not establish real inbox delivery, custom domain/DNS configuration or a wall-clock expiry contract; expired-action-code recovery text is tested using the SDK error category. Live expiry/delivery/template settings need a separately approved operator rehearsal, not a real-account test inside Codex.
