## Provider recommendation

Use **Resend**, through its server-side HTTPS API. This needs no additional SDK, SMTP connection, Firebase Functions deployment or client email configuration. It offers provider idempotency keys and signed Svix delivery events. SendGrid and Postmark are reasonable alternatives but would add a different integration without reducing this application's queue/authorization requirements. Before activation, the owner must confirm current Resend pricing, domain ownership, data processing/retention terms, regional suitability and the documented **24-hour idempotency retention**. The worker stops automatic retries at 23 hours to leave a margin. If the provider contract changes, do not activate until the policy and tests are updated.

Official operator references: [sending](https://resend.com/docs/api-reference/emails/send-email), [idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), [webhooks](https://resend.com/docs/dashboard/webhooks/introduction), [test addresses](https://resend.com/docs/dashboard/emails/send-test-emails). No external provider request is needed for local tests.

## How delivery works

1. Existing consult/application browser code still commits its private original and client projection. No email service request is added to that path. Outages cannot reject an otherwise valid submission.
2. A scheduled **server-only** `GET /api/internal/notifications` discovers new private `consultRequests`, `membershipApplications`, and trusted `notificationMessageReceipts`. It requires an exact `CRON_SECRET` bearer (at least 32 characters); Firebase user tokens cannot invoke it. There is no browser enqueue endpoint or caller-supplied email recipient.
3. A durable cyclic document-ID cursor scans up to 25 records per collection per tick. It uses authoritative Firestore **document creation metadata**, not caller-controlled `createdAt`. The activation UTC watermark excludes historical originals and projection-only migration backfills. Cycling catches new IDs inserted before a cursor. This trades simple single-field queries for repeated reads: schedule frequency and backlog/read costs must be capacity-tested before launch. Pagination and queue inserts are restartable; cursor loss only repeats deduplicated discovery.
4. A deterministic queue key includes source path, notification kind, studio target index and configuration generation. Multiple studio recipients receive independent emails, preventing address disclosure and partial-batch retry duplication. No message/health/intake text, email address, bearer token or provider response body is stored in queue tracking. Queue records contain private source IDs, status, numeric retry times/counts, hashes, provider ID and sanitized failure reason.
5. The worker revalidates the source and matching owner-scoped projection, enabled Auth owner, and, for replies, server receipt, immutable message digest, active admin record, enabled sender Auth and matching conversation owner/view. Client recipients come **only from verified Firebase Auth email**, never CRM/form email or association matches. Unverified/missing/disabled owners and unreviewed legacy records are held. Studio alerts may be sent for an existing enabled owner even when the client's email is unverified.
6. A transaction claims a 60-second lease before sending. Retries use the same persistent key and an identical envelope hash; changed recipient/template/configuration is held. Send attempts have a 10-second network timeout and exponential backoff (30 seconds, capped at an hour), at most eight provider attempts (or 16 total claims when validation itself repeatedly fails) and a 23-hour window from first attempt. Each tick attempts at most 20 due jobs and stops starting jobs after its time budget. Configure a scheduler that permits frequent invocations; no schedule is installed in this PR.
7. Successful API acceptance is **accepted**, never called delivered. Signed webhooks mark delivered, delayed, bounced, complained or failed. Event IDs are deduplicated; delayed/out-of-order delivered events cannot overwrite bounce/complaint. Bounces/complaints create private hashed-recipient suppressions. Unmatched early webhooks return 503 for provider retry; permanent unmatched events require operator reconciliation.

**Duplicate protection has an operational boundary:** database leases alone cannot promise exactly-once external side effects. The provider's idempotency retention closes the crash/timeout gap inside the retry window. At expiry or retry exhaustion, an uncertain job becomes `held`; do not reset its first-attempt time or generate a new key. Reconcile with the provider before authorizing any replacement. A crash before the first network call is conservatively treated the same way. Queue/job deduplication tombstones must be retained; deleting terminal jobs can allow rediscovery and duplicates. A server-only configuration fence refuses a changed generation unless its new activation watermark is later than the previous worker tick. Preserve this fence across restore as well; reactivation still requires a reviewed watermark and reconciliation.

## Admin messaging compatibility and privacy

All five existing admin reply call sites share `lib/adminFirestore.js` (`AdminInbox`, `AdminIntakeDashboard`, `AdminMembershipRequests`, `AdminMembershipOffers`, `AdminMembershipOfferResponses`). Its `addDoc(messages, ...)` now calls `POST /api/admin/messages` with a Firebase bearer token, generated stable document ID, conversation ID and body. The server verifies revocation and rechecks `adminUsers/{uid}.active` inside the transaction. It derives client identity and relationship IDs from the conversation, validates linked source ownership, stamps authenticated sender identity and server time, then atomically creates original, projection, receipt and unread/preview changes. It returns the ordinary Firestore reference to existing callers. Other collection helpers and client messaging are unchanged.

The existing components continue their workflow-specific status/review updates after sending; a later status update failure does not roll back the already recorded message. Replaying the **same ID and same request** is idempotent. A deliberate new user action with a new ID is a new message; transport ambiguity in the browser can still need operator confirmation before manually resending a reply. This is distinct from Firestore event/provider retries, which use the persisted notification key.

Legacy conversations **without** a reviewed portal projection reject server replies rather than publish legacy messages/health text as a side effect. They need the approved privacy migration first. Existing browser rules still permit admins to create ordinary messages directly; such writes lack the server-only receipt and **never generate email**. No rules are changed here. Old frontend versions must be retired at coordinated cutover. Do not weaken rules to restore legacy unreviewed access.

Email templates use black, white and blue branding. Their only links are generic HTTPS `/tattoo-portal` sign-in and `/admin`; there are no login tokens, client IDs, conversation IDs, previews, attachments or private contents. A portal session and Firestore ownership authorization are still required. Internal CRM originals/notes stay admin-only. No studio-managed file creates an Auth account or changes account links. Payments, membership charging and financial history are untouched.

**Account verification limitation:** existing signup does not establish verified ownership of an email address. Those client confirmations/reply alerts remain held with `verified_email_required`; studio alerts and portal recording continue. A separately reviewed verification UX/operator process is required before promising email confirmations to every newly registered client. Do not send to an unverified form address to bypass this boundary. Held jobs are never automatically replayed after verification; review age/ownership and authorize any new notice separately.

## Configuration (server only)

Never prefix these with `NEXT_PUBLIC_`, commit real values, or enter provider credentials in Codex.

| Setting | Purpose / safe default |
| --- | --- |
| `NOTIFICATIONS_MODE` | `off` by default; `test` is emulator-only and has no network transport; `resend` is production-context-only |
| `NOTIFICATIONS_ENABLED` | Must be exact `true` for provider transport; keep `false` until separately approved |
| `NOTIFICATIONS_AUDIENCE` | Defaults `staging`: all provider-bound recipient addresses replaced by **`delivered@resend.dev`**; `live` requires separate approval |
| `NOTIFICATION_ACTIVATED_AT` | Explicit reviewed ISO UTC watermark; required whenever mode is not off; choose a new future cutover watermark for live activation |
| `NOTIFICATION_FROM` | Bare verified-domain sender address; brand display is in template; explicit value required for provider mode |
| `NOTIFICATION_STUDIO_RECIPIENTS` | Comma-separated owner-approved studio inboxes, maximum 10; explicit for provider mode |
| `NOTIFICATION_PORTAL_ORIGIN` | Explicit canonical HTTPS production origin, no path/query/user info; loopback-only for local test |
| `CRON_SECRET` | Unique server scheduler bearer secret, minimum 32 characters |
| `RESEND_API_KEY` | Restricted sending key; required only in separately approved provider mode |
| `RESEND_WEBHOOK_SECRET` | Endpoint-specific Svix signing secret, required for delivery reporting |

Provider mode also requires the existing genuine Vercel Production Firebase context and matching Admin project `fawcett-website-sandbox`. Preview/local contexts cannot opt into live Firebase/provider delivery. Local test addresses must use `@example.test`. A production-context staging configuration must be rehearsed **outside Codex only after separate approval**, never by connecting a Preview deployment to real data.

## Pause, recovery and operational limitations

Set mode off and disable the scheduler to stop **new** sends; signed delivery webhooks remain available while their signing secret is configured, so prior acceptances can still be reconciled; an already in-flight external request may complete. Do not delete queue rows, receipts, suppressions or cursors, reset first-delivery timestamps, or auto-release held jobs. Before resuming, reconcile provider acceptances, signed delivery events and unknown outcomes. Preserve event/key metadata across backups/restores; rolling back just the queue can cause duplicates. For a prolonged outage, leave valid intakes in place; review held jobs rather than resend automatically after the provider retention period. Provider suppression/complaint policy also applies outside this application.

No mechanism can retract an email already accepted or erase a link from an inbox. Restore/rollback privacy rules and frontend only under the coordinated Phase 4A runbook; notifications cannot make a legacy frontend/rule combination safe. The queue does not contain message bodies, but private identifiers and recipient hashes still require server-side access controls and backup protection. Keep deduplication tombstones for at least as long as eligible sources can be discovered; design any later retention/compaction change separately.

Review blockers: Phase 4A approval/cutover, verified-email UX/policy, provider account/DNS/signature contract confirmation, external staging constraints, owner-approved sender/recipients/canonical origin, scheduler provisioning/capacity/alerts, IAM review, and approved activation. **No production access, settings changes, rules deployment, real email, payment activation or automatic merge is authorized by this implementation.**
